# 壓力測試

分成兩組，都用 `Run-StressTest.ps1` 執行：
- **多人使用**（`-Suite multiuser`，預設，`stress.mjs`）：見下方「情境」。
- **大量資料**（`-Suite large`，`large-data.mjs`）：把資料表灌到上萬筆後量測，見「大量資料測試」。

多人使用測試模擬多位使用者同時操作網頁版，並模擬舊系統 (VFP) 同時修改 DBF，檢查四件事：
- 回應時間與錯誤率
- DBF 與 PostgreSQL 快照是否一致
- 自動取號是否重複
- 同時存檔是否互相覆蓋

測試需要 VFP COM (`w3000_dbf.dll`) 與 DBF 資料，CI 無法執行，請在開發機或伺服器上手動跑。

## 執行

1. 啟動後端與 LocalAgent，例如 `pnpm dev`，或使用已安裝的服務。
2. 在專案根目錄執行：

```powershell
.\tests\stress\Run-StressTest.ps1
.\tests\stress\Run-StressTest.ps1 -Users '1,5,10,20,30' -Duration 20 -Burst 20 -Rounds 20
.\tests\stress\Run-StressTest.ps1 -Scenarios 'read-load,legacy-race' -ApiUrl http://127.0.0.1:5017
.\tests\stress\Run-StressTest.ps1 -Suite large -Rows '10000,30000' -Tables 'buyinv,recmom,customer' -Users '1,5,10'
```

`Run-StressTest.ps1` 會依序：
1. 把 `C:\w3000\comm` 的 DBF、CDX、FPT 複製到 `%TEMP%`。
2. 用 subst 把複本掛到一個空的磁碟機代號（預設從 W: 往前找）。
3. 執行 `stress.mjs`；`-Suite large` 時改執行 `large-data.mjs`。
4. 不論成功或失敗，最後都會卸載磁碟機，刪除 PostgreSQL schema `"<代號>:/w3000/comm"` 與 `dictionary.w3000_dbf`、`dictionary.w3000_dbf_dupkey` 中該代號的列，再刪除複本。

報告寫在 `tests/out/stress/`（Markdown 與 JSON，不納入版本控制）。有任何 FAIL 時，結束代碼為 1。

| 參數 | 預設 | 說明 |
| --- | --- | --- |
| `-Suite` | `multiuser` | `multiuser` 或 `large` |
| `-Users` | `1,5,10,20` | 多人讀取依序測試的同時使用者數 |
| `-Duration` | `15` | 多人讀取每個級數的秒數 |
| `-Burst` | `10`（`large` 為 `5`） | 其他情境同時送出的請求數 |
| `-Rounds` | `20` | `legacy-race` 的輪數 |
| `-Scenarios` | `all` | 只跑部分情境，以逗號分隔（`multiuser`） |
| `-Rows` | `10000,30000` | 依序灌到的筆數（`large`） |
| `-Tables` | `buyinv,recmom,customer` | 要測的資料表（`large`） |
| `-ApiUrl` / `-AgentUrl` | `http://localhost:5007` / `http://127.0.0.1:5009` | 後端與 LocalAgent 的位址 |
| `-KeepCopy` | 關 | 測完保留 DBF 複本，方便檢查 |

模擬舊系統寫入要用 `localagent\bridge\lazarus\DBFBridge.exe`，這個檔案不在版控內。在 git worktree 等沒有這個檔案的目錄執行時，先從主目錄複製過來 (已在 `.gitignore` 內)。

`stress.mjs`、`large-data.mjs` 也可以直接執行，例如 `node tests/stress/stress.mjs --drive V`。為了保護正式資料，下列情況會拒絕執行：
- 磁碟機代號是 C。
- 磁碟機不是 subst 掛上的。如果確定是複本，可以加 `--allow-non-subst` 略過這項檢查。
- 磁碟機與後端目前的預設磁碟機相同。

## 情境

| 名稱 | 模擬什麼 | 怎麼判定 |
| --- | --- | --- |
| `cold-sync` | 新的磁碟機第一次使用時，多人同時開 4 個畫面 | 全部回 200，且每張表的快照筆數等於 DBF 筆數 |
| `agent-queue` | 直接對 LocalAgent 同時送出多個 checksum | 只記錄數據（INFO）：單次耗時與排隊時間 |
| `read-load` | N 位使用者不停開 6 個清單畫面，沒有思考時間，代表最壞情況 | 有錯誤為 FAIL；p95 超過 3 秒為 WARN |
| `stampede` | 舊系統改了會計師或客戶資料後，多人同時開清單 | 全部成功，且沒有人拿到舊資料 |
| `dup-key` | 多人同時新增同一個會計師代號；另測舊系統剛新增某代號、快照還沒重灌時，網頁再新增同一代號 | DBF 只能有 1 筆，恰好 1 人成功、其餘收到 409；舊系統已新增的代號回 409 |
| `numbering` | 多人同時新增委任書條文（5-6）、共用摘要（4-5）、收費單（2-4）；再對同一張收費單同時新增 2 筆明細 | DBF 中 seq、serial、單號沒有重複，每個請求都成功，DBF 新增的筆數等於成功的回應數；明細 2 筆都要新增成功（`rno` 本來就會重複，不能被重複代號檢查擋下） |
| `lost-update` | 甲、乙打開同一筆資料，甲改電話後存檔，乙改傳真後存檔 | 甲修改的電話仍保留 |
| `legacy-race` | 網頁存檔的同時，舊系統改另一筆資料 | 網頁每輪都讀得到舊系統的修改 |
| `consistency` | 全部情境跑完後 | 網頁讀到的資料與 DBF 一致 |

「舊系統修改」的模擬方式：另外啟動一個 32-bit `DBFBridge.exe` 程序，執行 VFP `REPLACE` 或 `INSERT INTO`（預設用 `localagent/bridge/lazarus/DBFBridge.exe`，可用 `--bridge` 指定）。這個程序和真正的 VFP 工作站一樣，不經後端，也不經 LocalAgent 的隊列，所以 PostgreSQL 與 checksum 字典都不會更新，寫入時間點也不受 LocalAgent 排隊限制。

## 大量資料測試（`-Suite large`）

`large-data.mjs` 會在測試複本上，用另外啟動的 DBFBridge 執行 VFP `COPY TO` / `APPEND FROM`，把資料表依序灌到 `-Rows` 指定的筆數。索引 (CDX) 由 VFP 一併更新；新增記錄的主鍵改成 `Z` 加 RECNO，不會和原有資料重複。每灌到一級就量測下列項目：

| 項目 | 量測方式 | 判定 |
| --- | --- | --- |
| checksum | 直接對 LocalAgent 算 3 次，並用 Node `crypto` 算同一個檔案作為對照 | INFO |
| 重灌腳本 | 直接呼叫 LocalAgent `get_pg_script`（DATA），記錄 VFP 產生時間與腳本大小 | 失敗為 FAIL |
| 重灌後開清單 | DBF 剛變動後第一次開清單（整表重灌） | 失敗或筆數與 DBF 不符為 FAIL；超過 10 秒為 WARN |
| 沒變動開清單 | 連開 3 次取中位數，並記錄回應大小 | 超過 3 秒為 WARN |
| 多人開清單 | `-Users` 各級人數不停開清單 `-Duration` 秒 | 有錯誤為 FAIL；p95 超過 3 秒為 WARN |
| 舊系統改一筆後多人開清單 | 模擬舊系統改一筆，`-Burst` 人同時開清單 | 有人失敗或看到舊資料為 FAIL；全部超過 30 秒為 WARN |
| 重灌時開小表 | 大表重灌期間，每 0.5 秒開一次會計師清單 | 最慢超過 3 秒為 WARN |
| 網頁存一筆 | 用畫面的存檔 API 改一筆，連做 3 次；存完再開一次清單 | 存完後開清單明顯變慢（被當成外部修改而重灌）為 WARN |
| 多人同時存檔 | `-Burst` 人各改不同的一筆、同時送出，連做 3 輪；每輪後開一次清單，最後核對清單與 DBF | 有人失敗、清單或 DBF 不是最後存的值為 FAIL；存完後被整表重灌，或一輪超過 6 秒為 WARN |
| 客戶變動後存收費單（只測客戶） | 舊系統改一筆客戶後，存一張收費單（2040 存檔前會同步客戶表） | 失敗為 FAIL；超過 10 秒為 WARN |
| 快照過期時新增（只測客戶，快照同步不了時才跑） | 新增一個 DBF 已有、但快照沒有的代號 | DBF 出現重複代號為 FAIL |
| 隊列塞住時存檔（同上） | 觸發一次整表重灌，4 秒後存一筆客戶，等 LocalAgent 做完後讀 DBF | 回覆和 DBF 不一致為 FAIL：回失敗但 DBF 已寫入，或回成功但 DBF 沒寫入（回「無法確認」時兩種都算一致） |

「存完後被整表重灌」用時間判斷：存完後開清單比沒有變動時慢 3 倍以上，而且多 1 秒以上。

某一級的快照同步不了時（API 回 200，但筆數和 DBF 不同），量完「卡住時」再開一次清單與開小表的時間，就跳過其他項目與更大的級距。

可測的資料表：

| `-Tables` | 畫面 | 清單 API | 存檔 API |
| --- | --- | --- | --- |
| `customer` | 2010 客戶 | `GET /api/wbase2010`，全表 | 讀單筆後整筆 `PUT /api/wbase2010/{no}`（改 fax） |
| `buyinv` | 3020 進項發票 | `GET /api/wbase3020?period=&times=`，只列筆數最多的一期 | 讀單筆後整筆 `PUT /api/wbase3020/{期別}/{次}/{no}`（改簡稱） |
| `recmom` | 2040 收費單 | `GET /api/wbase2040`，全表 | `PUT /api/wbase2040/{rno}`（改收款人，只挑未收款的單） |

## 修正同步遺失後

修正內容：
- **LocalAgent：** 在同一個隊列項目內讀取寫入前後的 `.dbf`，回傳 `checksumBefore`、`checksumAfter`。同時比對位元組，若有這次寫入以外的變動，就回傳 `otherChanges`。
- **後端：** 控制器改呼叫 `CommitWriteChecksumAsync`，以條件式 UPDATE 更新字典。只有同一請求的寫入首尾相接、沒有其他變動，而且字典仍是寫入前的值時才更新；否則不動字典，讓下次讀取重灌。

相同參數下重跑（`-Rounds 30`）的結果：

| 情境 | 修正前 | 修正後 |
| --- | --- | --- |
| `legacy-race` | 30 輪中 22 輪遺失 | 30 輪中 0 輪遺失 |
| 其他情境 | 見上表 | 結果與修正前相同。dup-key、numbering、lost-update 仍為 FAIL，要另外修正 |

修正後的速度數據比上表慢約 25%（單次 checksum 約 90 ms）。讀取路徑並沒有改；直接啟動 DBFBridge.exe 也要 80～90 ms，所以是測試當時電腦本身較慢。

修正後仍無法偵測一種情況：網頁與舊系統在同一個約 80 ms 的時間窗內，修改同一筆記錄的同一個欄位。此時位元組變動落在本次寫入的範圍內，無法分辨是誰改的。

各欄說明：
- **進項發票的清單：** 3020 只列筆數最多的那一期，所以清單只有 789、2,367、7,890 筆。
- **「舊系統改一筆後 5 人同時開」：** 這一欄超過 60 秒時，表示有人的重灌已經逾時。那幾個人看到的仍是正確資料，因為重灌已由第一個人完成；但他們放棄的工作還留在 LocalAgent 裡。進項發票 10 萬筆時，LocalAgent 又花了 173 秒，才做完這些工作。
- **重灌腳本的時間不穩定：** 同一份 1 萬筆客戶，四次量測分別是 17.7、18.0、18.5 與 41.8 秒；進項發票 3 萬筆兩次分別是 6.3 與 11.0 秒。單人重灌離 60 秒逾時的距離，比上表看起來更近。

客戶 1 萬筆時還能用，但已經很慢：
- **平常開清單：** 每次要 0.6 秒，10 人同時開時 p95 是 4.3 秒。
- **舊系統改一筆後：** 5 人同時開客戶清單，最後一人等了 64 秒。
- **重灌期間：** 別人開會計師清單最慢要 19.5 秒；之後 LocalAgent 還要 33 秒，才做完後端已經放棄的工作。
- **網頁存檔：** 存一筆要 0.6 秒。5 人同時存不同的客戶，每輪 2.9 秒才全部存完，因為每次寫入都要在 LocalAgent 裡讀寫入前後的整個 DBF (35 MB)，排隊依序做。3 輪都沒有觸發重灌，`CommitWriteChecksumAsync` 在大表與多人同時存檔時都正常。
- **其他畫面的存檔也被拖慢：** 舊系統改了一筆客戶後，存一張收費單要 23.6 秒，因為 2040 存檔前會先同步客戶表，等於替客戶表整表重灌。

客戶 3 萬筆時，這張表就同步不了，而且會拖垮全公司：
- **資料停在舊快照：** VFP 產生重灌腳本要 172 秒，後端等 LocalAgent 60 秒就放棄。API 照樣回 200，但內容一直停在 1 萬筆的舊快照。
- **每次開畫面都卡 60 秒：** 之後每次開客戶畫面都重試、都逾時。
- **其他畫面也受影響：** 後端放棄的重灌仍在 LocalAgent 裡執行，排在後面的讀寫全部要等。會計師清單只有 4 筆，也要 60 秒才回應。
- **新增客戶會在 DBF 產生重複代號：** `Z0030000` 在 DBF 裡已經有了，只是快照沒有。從網頁新增這個代號，API 回 201，DBF 從 1 筆變成 2 筆。後端新增前只查快照，判定不存在就 `INSERT`。
- **網頁說存檔失敗，其實已經寫入：** 重灌把 LocalAgent 隊列塞住時存一筆客戶。後端等了 60 秒，回 400「地端 DBF 寫入失敗」；但這筆寫入還排在 LocalAgent 裡，78 秒後仍寫進 DBF。PostgreSQL 與 checksum 字典都沒有這次修改。

## 修正存檔問題後

修正內容：
- **LocalAgent 新增前查重：** `INSERT` 的 VFP 腳本先 `LOCATE` 找未刪除、鍵值相同的記錄，有就回 `DUPLICATE_KEY`，不新增。鍵值本來就會重複的新增（收費明細以 `rno`、會計摘要以 `accno`）由後端傳 `allowDuplicateKey`；鍵值含 `RECNO()` 時不檢查。
- **LocalAgent 排隊逾時不寫入：** 後端在寫入請求帶 `queueTimeoutMs`（45 秒，比後端呼叫 LocalAgent 的 60 秒逾時短）。寫入在隊列裡等超過這個時間，或後端已斷線，就不執行，回 `AGENT_BUSY`。
- **後端：** 自己等到 60 秒逾時時回 `WRITE_UNCONFIRMED`，訊息是「無法確認這次是否已寫入 DBF，請重新整理畫面確認」，不再說成寫入失敗（`DbfWriteResult.FailureText`、`IsUnconfirmed`）。

實測（同一台開發機）：

| 情境 | 修正前 | 修正後 |
| --- | --- | --- |
| 客戶 3 萬筆、快照停在舊版時新增 DBF 已有的代號 | 回 201，DBF 多一筆重複代號 | 回 400「customer.dbf 已有 Z0030000 的資料，這次沒有新增」，DBF 仍是 1 筆 |
| 重灌塞住 LocalAgent 時存一筆客戶 | 60 秒後回「寫入失敗」，78 秒後 DBF 仍被寫入 | 45 秒後回「LocalAgent 忙碌…這次沒有寫入 DBF」，DBF 沒有寫入 |
| `dup-key`：10 人同時新增同一會計師代號 | DBF 寫入多筆 | 1 人成功，9 人收到「已有 Z0 的資料」，DBF 只有 1 筆 |
| `numbering`：10 人同時新增委任書條文 | 全部成功，seq 全部相同 | 1 人成功，9 人收到「已有 4 的資料」，seq 不重複 |
| `numbering`：同一張收費單同時新增 2 筆明細（新加的檢查） | - | 2 筆都成功 |

仍未修正：
- **取號：** 共用摘要的 serial 沒有唯一鍵，仍會重複；委任書條文雖然不再重複，但同時新增時只有一人成功。要在 VFP 腳本內取號才能兩者兼顧（見「建議修正」第 2 項）。 → 已在下一節「修正重複代號與取號後」以 VFP 取號修正。
- **`lost-update`：** 後存檔的人整筆覆蓋，與這次修正無關。
- **大表同步不了本身：** 客戶 3 萬筆仍同步不了，存檔在 LocalAgent 塞住時會等 45 秒後才收到「這次沒有寫入」。
- **和舊系統同時新增同一代號：** 查重與新增之間有幾毫秒的空窗，沒有用 `FLOCK()`。 → 下一節改為鎖檔頭後已無空窗。

## 修正重複代號與取號後

修正內容：

**LocalAgent**

`POST /api/dbf/write` 的 INSERT 新增 `unique` 與 `autoNumber` 兩個選項，詳見 `localagent/README.md`。帶這兩個選項時，VFP 腳本依序做三件事：
1. 先以 `RLOCK("0")` 鎖住檔頭。
2. 再以 `LOCATE` 確認代號不存在，或以 `CALCULATE MAX()` 取號。都不含已刪除的記錄。
3. 最後 `INSERT`。代號已存在時回 `DUPLICATE_KEY`，取到的號碼回傳給後端。

用檔頭鎖而不用 `FLOCK()`，原因是實測結果不同：
- 另一個程序鎖著某筆記錄時，`FLOCK()` 會失敗，`RLOCK("0")` 仍會成功。所以舊系統有人在編輯資料時，網頁還是能新增。
- 另一個程序持有檔頭鎖時，`INSERT INTO` 等約 2 秒後以 VFP 錯誤 108 失敗。所以舊系統的 `APPEND` / `INSERT` 會和網頁的新增排隊。

**後端**

- 先查後插的新增都改為帶 `Unique`，重複時回 409，涵蓋 1020、1030、1050~1080、2010、3010、3020、4010、4020 `acc_st`。
- 取號改由 VFP 執行：5-6 `bsdesc.seq`、4-5 `descrip.serial`、4010 `serial`、2-4 收費單號。
- 5-6 與 4-5 的新增先同步快照：原本在新磁碟機第一次新增會 500，因為快照表不存在。
- 寫 PostgreSQL 前先確認快照裡沒有同一個 `_record_number`：寫完 DBF 後，快照可能已被別人的請求重灌。
- 5-6 的 `_record_number` 改用 DBF 回傳的 RECNO，原本是快照最大值 + 1。

**測試**

- `dup-key` 加測一種情況：舊系統直接在 DBF 新增某代號 (快照還沒重灌)，網頁再新增同一代號。
- `numbering` 改為三項都要成立才 PASS：每個請求都成功、DBF 新增的筆數等於成功的回應數、號碼不重複。原本只檢查重複，所以在新磁碟機上 20 個請求全部 500 時也算 PASS。

## 分析

### 效能：全公司的讀寫排成同一列

- **LocalAgent 一次只執行一個動作：** 伺服器上只有一個 LocalAgent，它把所有 DBF 動作（PING、CHECKSUM、READ、GET_PG_SCRIPT、寫入）排成一列，見 `localagent/agent.js` 的 `callDbfBridge`。每個動作都會重新啟動一次 32-bit `DBFBridge.exe` 並載入 VFP COM，約 70 ms。
- **每次讀取都要排隊：** 後端每次讀取都會先呼叫 `EnsureTableSyncedAsync` 計算 DBF 的 SHA256，所以每次開畫面都要進這一列。不論多少人使用，全公司每秒最多約 14 個請求；同時操作的人數增加時，每個人的等待時間跟著拉長，大約是「人數 × 72 ms」。有些畫面一次要同步多張表，例如 2040、4020、5010，等待時間還要乘上表數。
- **重灌不會合併：** 舊系統改過 DBF 後，第一批同時進來的請求都會發現 checksum 不同，各自整表重灌一次。後端記錄顯示，20 人同時開客戶清單時，客戶表被重灌了 20 次，每次約 0.55 秒，依序排隊，最後一人等了 14.4 秒；第一次使用新磁碟機時也是同樣的情形。客戶資料越多，重灌越慢。後端呼叫 LocalAgent 的逾時是 60 秒，超過就會失敗。

以 5～15 人的事務所來說，平常的讀取還能接受。比較需要注意的是上班時間大家同時開畫面，以及舊系統剛改過大表的時候。

### 資料量：上萬筆以後

見「大量資料實測結果」。慢不慢主要看 DBF 的檔案大小，筆數是次要的：收費單 3 萬筆只有 5.7 MB，重灌 4 秒；客戶每筆 3.7 KB，1 萬筆就有 35 MB，重灌要 25 秒。

1. **重灌時間比資料量成長得快，客戶約 1.8 萬筆、進項發票約 10 萬筆以後就同步不了**
   - **原因：** 重灌腳本由 VFP COM 的 `Data_to_PG_Script` 一次組成一個大字串。
   - **實測：** 筆數變成 3 倍時，產生時間變成 3～9 倍：
     - 客戶 1 萬筆的腳本 12.9 MB，要 18 秒；3 萬筆的腳本 38.6 MB，要 159～172 秒。
     - 進項發票 1 萬筆要 2.1 秒，3 萬筆要 6～11 秒，10 萬筆要 55 秒。
   - **門檻：** 後端呼叫 LocalAgent 的逾時是 60 秒（`Program.cs`）。依客戶表的兩個數據推算，腳本約 23 MB 就會超過，大約是 1.8 萬筆客戶；進項發票 10 萬筆已經接近。這是只有一個人的情況，多人同時重灌時會更早超過。
   - **時間不穩定：** 同一份 1 萬筆客戶，有一次要 41.8 秒（其他三次約 18 秒）。電腦忙的時候，1 萬筆客戶就可能逾時。
   - **其他逾時：** PostgreSQL 執行腳本用 Npgsql 預設的 30 秒逾時（1 萬筆客戶時約 5 秒）；`runDbfBridge` 則完全沒有逾時。
2. **重灌失敗後不會自己恢復，還會拖垮全公司**
   - **資料靜悄悄地停在舊版：** `EnsureTableSyncedAsync` 失敗時，控制器照樣讀舊快照、回 200，畫面上看不出資料是舊的。
   - **每次讀取都重試：** 之後每次讀取都重算 checksum、重試重灌，每次都逾時。
   - **隊列越積越多：** 後端逾時後，LocalAgent 不知道請求已經被放棄，仍會照樣產生腳本，所以隊列消化不完。
   - **連帶影響：** 所有畫面的 DBF 讀寫都要排在這些工作後面，包括只有幾筆的小表，以及網頁存檔。
3. **快照停在舊版、或 LocalAgent 塞住時，存檔會弄壞資料**（客戶 3 萬筆實測，已修正，見「修正存檔問題後」）
   - **重複代號：** 2010 新增前只查 PostgreSQL 快照，判定不存在就 `INSERT` 進 DBF。快照停在舊版時，DBF 已有、但快照沒有的代號會被再新增一次，API 還回 201。`PUT` 也一樣，找不到舊資料就改成 `INSERT`。這和「同時新增同一代號」（`dup-key`）是同一個原因，但這裡只要一個人就會發生。
   - **存檔結果不明：** 後端等 LocalAgent 60 秒就放棄，回 400「地端 DBF 寫入失敗」。但這筆寫入還排在 LocalAgent 的隊列裡，之後照樣寫進 DBF，PostgreSQL 與 checksum 字典則沒有這次修改。使用者以為沒存到，可能再存一次或改用舊系統輸入；如果是新增，再按一次就多一筆。
   - **觸發條件：** 只要 LocalAgent 的積壓超過 60 秒就會發生，不限於同步不了的表。例如進項發票 10 萬筆時，舊系統改一筆後有 5 人同時開清單，LocalAgent 就積壓了 173 秒。
4. **一張大表會拖慢其他畫面的存檔**
   - **原因：** 收費單（2040）存表頭、批次產生、查客戶與列印前，都會同步客戶表。4020 的三個清單也都會同步客戶表。
   - **實測：** 客戶 1 萬筆、舊系統剛改過一筆客戶時，存一張收費單要 23.6 秒，平常只要 0.7 秒。客戶表同步不了時，每次存收費單都要等 60 秒逾時。
   - **多人同時存檔本身沒問題：** 5 人同時存不同的記錄，三張表每一級都沒有觸發重灌，DBF 與清單都是最後存的值。只是每次寫入都要在 LocalAgent 裡讀寫入前後的整個 DBF，依序排隊；客戶 1 萬筆時，5 人同時存要 2.9 秒才全部存完。
5. **checksum 由 VFP 計算，慢 10～20 倍**
   - **實測：** DBFBridge 的 `CheckSum_SHA256` 約 90 MB/s。客戶 1 萬筆時要 407 ms，Node `crypto` 算同一個檔案只要 27 ms。
   - **影響：** 每次讀取都要算一次，而且要排隊。客戶 1 萬筆時，全公司每秒最多只能開約 2.5 次客戶畫面。
6. **舊系統改一筆，就要整表重灌**
   - **原因：** 只要 checksum 不同，就從頭重灌整張表，而且多人同時讀取時不會合併成一次（見上一節）。
   - **影響：** 表越大，每次舊系統存檔後，網頁的第一批使用者就要等越久。客戶 1 萬筆、5 人同時開清單時，最後一人等了 64 秒。
7. **清單一次載入全表，前端沒有虛擬捲動**（依程式碼分析，未實測瀏覽器）
   - **後端：** 清單 API 都沒有分頁。客戶 1 萬筆時，每次開 2010 都要傳 5.5 MB 的 JSON。
   - **表格元件：** `FoxProGridV2`、`FoxProGridCard` 會把全部列畫出來，沒有 memo。游標移動或編輯時每按一鍵，整張表都會重新渲染。1 萬筆大約有 50～60 萬個 DOM 節點。只有 `FoxProGridBill`（AG Grid）有虛擬捲動。
   - **存檔後重抓全表：** 1020～1080、2010、3010、3020 每存一格，都會重抓整張表再重繪；在 `FoxProGridV2` 裡每按一次 Enter，就是一次 PUT 加上一次全表 GET。
   - **查詢彈窗與列印：** 查詢彈窗（`SearchModal` 與各模組自製的彈窗）一開就畫出全部結果，每按一鍵就重新過濾一次。F7 列印預覽會把全部資料畫成一張表。
8. **其他發現**
   - **3020、3050、3060 不同步客戶表：** 這三個畫面直接讀客戶快照，但只同步 buyinv。在新的磁碟機上，如果還沒有人開過 2010，3020 會回 500（`relation ... customer does not exist`）；舊系統改了客戶資料後，這些畫面會一直顯示舊的公司名稱與地址，直到有人開 2010。
   - **重灌時整份腳本寫進日誌：** EF Core 以 Information 等級記錄每個 SQL 指令，重灌時整份資料腳本都會寫進日誌。1 萬筆客戶每次重灌約 13 MB，內容含身分證號、電話。跑一次完整的 `-Suite large`（約 25 分鐘），後端日誌就累積了 260 MB。

### 正確性：同時寫入時會出錯

1. **舊系統的修改可能永遠不會同步到網頁**（`legacy-race`，已修正）
   - **原因：** 網頁存檔依序做三件事：寫 DBF、寫 PostgreSQL、重新取 checksum 存進字典。如果舊系統的修改剛好發生在第一步和第三步之間，字典記下的 checksum 已經包含舊系統的修改，但 PostgreSQL 沒有。之後每次讀取都會判定「沒有變動」而不重灌。
   - **後果：** 網頁會一直顯示舊資料，直到 DBF 下次被修改。如果使用者又在網頁上存了同一筆資料，網頁送出的是整筆資料，會把舊系統的修改從 DBF 蓋掉，等於永久遺失。
   - **頻率：** 實測 20 輪有 11 輪發生，在新舊系統並行的期間不是罕見情況。
2. **同時新增同一代號，DBF 會出現重複記錄**（`dup-key`，已修正，見「修正存檔問題後」與「修正重複代號與取號後」）
   - **原因：** 新增前只查 PostgreSQL，然後直接 `INSERT` 進 DBF，而 DBF 沒有唯一限制。
   - **後果：** 收到 500 的使用者以為新增失敗，其實 DBF 已經寫入；如果再按一次，又會多一筆。之後依代號修改或刪除，只會找到第一筆。
3. **自動取號重複**（`numbering`，已修正）
   - **原因：** 委任書條文的 seq（`Wbase5010Controller`）、共用摘要的 serial（`Wbase4020Controller`）、會計科目的 serial（`Wbase4010Controller`），都是從 PostgreSQL 取最大值加 1，沒有任何鎖。
   - **後果：** 委任書條文的 seq 是主鍵，重複後只有第一筆看得到。共用摘要沒有唯一鍵，所以重複不會報錯，也不容易察覺。
   - **修正存檔問題後：** 委任書條文的 seq 不會再重複寫入 DBF（LocalAgent 新增前查重），但同時新增時只有一人成功，其他人收到「已有這個代號」。共用摘要仍會重複。
   - **例外：** 收費單（2040）在後端用 `SemaphoreSlim` 排隊，所以沒有重複。但這個鎖只擋得住同一個後端程序內的請求；舊系統同時開收費單，仍可能取到同一個單號。
4. **後存檔的人會覆蓋前一位的修改**（`lost-update`）
   - **原因：** 1020 等畫面存檔時送出整筆資料，後端用 `REPLACE` 把所有欄位寫回 DBF，沒有任何版本檢查。
   - **差異：** VFP 原本大多是逐欄寫回，所以舊系統沒有這個問題。
5. **未測項目：所有人共用一個預設磁碟機**
   - **原因：** `POST /api/systemconfig` 會改後端全域的預設磁碟機，也會寫回 `system_config.json`；沒有帶 `X-Data-Drive` 標頭的請求都用這個預設值。
   - **現況：** 目前前端的請求都帶這個標頭，所以影響有限。但任何一個人在設定畫面切換磁碟機，都會改到所有人共用的預設值。

### 建議修正（依影響排序）

1. ~~**寫入與取 checksum 合併成一個動作**~~：已修正，見「修正同步遺失後」。除了比對 checksum，也比對寫入前後的位元組，所以 VFP 在同一段時間改了別的記錄或別的欄位也偵測得到。
2. ~~**在 VFP 腳本內檢查主鍵與取號**~~：已修正，見「修正存檔問題後」(查重) 與「修正重複代號與取號後」(檔頭鎖與取號)。實作時沒有用 `FLOCK()`，改為鎖檔頭 `RLOCK("0")`：`FLOCK()` 只要有人鎖著任何一筆記錄 (例如舊系統正在編輯) 就會失敗，檔頭鎖只擋新增。
3. **重灌合併**：每張表（schema + table）加一個鎖。拿到鎖之後重新比對一次 checksum，相同就直接讀快照。這樣 20 人同時開畫面只會重灌一次。可以用後端的 `SemaphoreSlim` 字典，或 PostgreSQL 的 `pg_advisory_xact_lock`。
4. **存檔只送出有改的欄位，或加上比對舊值**：前端只送出有變動的欄位；或者把原始值一起送出，由 VFP 腳本在 `REPLACE` 前確認原始值沒有被改過，改過就回 409。
5. **DBFBridge 常駐**：改成常駐程序並重複使用 COM 物件，省掉每次約 70 ms 的啟動時間。

### 大量資料的建議修正（依影響排序）

1. **重灌改成線性時間**
   - **做法：** 由 LocalAgent 用 Node 直接讀 DBF（`agent.js` 已經能解析 DBF 檔頭與記錄），輸出資料列；後端再用 PostgreSQL `COPY` 匯入，取代 VFP 組成的大型 INSERT 腳本。
   - **效果：** 腳本產生時間不再隨資料量平方成長，3 萬筆客戶也不會超過逾時。
2. **重灌合併，並在背景執行**
   - **合併：** 同一張表同時只重灌一次（上一節第 3 項）。
   - **不讓使用者等：** 重灌進行中，其他請求直接回舊快照，並在畫面上標示「資料同步中」。
   - **LocalAgent：** 用戶端斷線時，丟掉還沒開始的隊列項目；DBFBridge 也要加上逾時。
3. **快照過期或 LocalAgent 逾時時，不要照常寫入**
   - **寫入不可在放棄後才執行（已完成）：** 寫入最多排隊 45 秒，逾時或後端已斷線就不執行，回 `AGENT_BUSY`。後端自己等到 60 秒逾時則回「無法確認是否已寫入」，不說成寫入失敗。
   - **新增在 VFP 腳本內檢查代號（已完成）：** 見上一節第 2 項。快照過期時，也不會在 DBF 產生重複代號。
   - **同步失敗要讓畫面知道（未做）：** 控制器檢查 `EnsureTableSyncedAsync` 的回傳值。失敗時讀取照樣回舊快照，但畫面要標示「資料可能不是最新」。`PUT` 在快照找不到舊資料時會改成 `INSERT`：現在會被 `DUPLICATE_KEY` 擋下，但使用者看到的是「已有這個代號」，不知道原因是快照過期。
4. **checksum 改由 LocalAgent 用 Node 計算**
   - **做法：** 格式和現在相同，`agent.js` 已經有 `dbfChecksum`。
   - **效果：** 速度快 10～20 倍；不需要啟動 DBFBridge，也可以不排進 VFP 的隊列。
5. **增量同步**：舊系統大多一次只改幾筆。比對每筆記錄，只更新有變動的列，不要整表重灌。
6. **清單分頁與虛擬捲動**
   - **後端：** 清單 API 加上分頁與伺服器端搜尋。
   - **前端：** `FoxProGridV2`、`FoxProGridCard` 加上虛擬捲動，並把列拆成 memo 元件。
   - **存檔：** 存檔後只更新那一列，不要重抓整張表。
7. **只在需要時同步別的表**
   - **2040：** 存表頭時，只有改了客戶代號才同步客戶表並查簡稱。
   - **3020、3050、3060：** 這三個畫面反過來，要在讀取 `CompanyMasters` 前呼叫 `EnsureTableSyncedAsync(..., "customer", ..., "no")`。checksum 改成 Node 計算後，多出來的成本很小。
8. **關閉 EF Core 的 SQL 指令日誌**：在 `appsettings.json` 把 `Microsoft.EntityFrameworkCore.Database.Command` 設成 `Warning`。
